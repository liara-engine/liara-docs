Searching dev and latest of every module.The whole site shares one search index, rebuilt on every deploy over the development build and the newest release of every module. Searching from an older release therefore answers with the current documentation rather than with that release: its pages stay online and keep their URLs, but they are not indexed. Keeping one index instead of one per published version is what stops search from growing every time a release is cut.

The documentation system

Every documentation site in the project — this one included — is built from one shared Astro preset, by one container image, and published to one hosting repository served at the edge. Nothing about a module’s documentation is specific to that module except its own prose, its own headers, and a manifest.

These pages are the documentation of that machinery. They are also, quite deliberately, a demonstration of it: everything Starlight gives an author is used here at least once, so a page you are reading doubles as a page you can copy.

Start here

Section titled “Start here”

If you are writing documentation for a module, you need Authoring a module’s documentation and nothing else. The rest is infrastructure you should be able to ignore.

If you are changing how the documentation looks or is built, start with The documentation pipeline: almost all of this repository is baked into the builder image, so the blast radius of a change here is every site at once.

If you are operating the site — rebuilding an old version, retiring one, chasing a deploy — go to CI and deployment.

Astro and Starlight

These pages describe the current toolchain. Documentation used to be built by mdBook (for prose) and Doxygen’s own HTML generator (for the API reference), stitched together by a shared theme and a runtime /shared-content/ bundle. All of that is gone: one Astro site per module now renders both halves, and the API reference is generated from Doxygen’s XML rather than its HTML.

Versions published by the previous toolchain are still online and still readable. They are brought over one at a time, on demand — see Rebuilding a version.

The five-line summary

Section titled “The five-line summary”

1 A module repository holds manifest.json, its prose in docs/, and — if it has a public API — a Doxyfile and headers.

2 CI runs the builder image against it. The image carries the shared Astro preset, so the module needs no Astro configuration of its own.

3 The build is fingerprinted: every asset moves into a site-wide content-addressed store, so two versions that produce identical bytes occupy one path.

4 The result is pushed to liara-docs under site/<repo>/<version>/, written once and never rewritten — which is what keeps a published URL working.

5 A deploy then refreshes the two things that span the whole site: the navigation index, and the search index.
