Authoring a module's documentation

This is the practical companion to The documentation pipeline: how to wire up documentation for a module so the shared toolchain picks it up, and what you can write once it does.

A module can ship a prose guide, a generated API reference, or both. Nothing below requires you to know anything about Astro.

1. What the builder looks for

Section titled “1. What the builder looks for”
  • Directoryyour-module/
    • manifest.json required — the module, its versions, and latest
    • README.md published under About
    • CHANGELOG.md published under About
    • LICENSE published under About
    • Directorydocs/ your prose guide, one file per page
      • index.mdx the section’s front page
      • getting-started.md
      • Directoryconcepts/
        • index.md
        • ecs.md
    • Doxyfile optional — enables the API reference
    • Directoryinclude/ the headers it is generated from
      • …
    • astro.config.mjs optional — rarely needed, see §5.2

Everything except manifest.json is optional. In practice every module has a guide; modules with a public C or C++ surface also have an API reference.

Tip

There is no SUMMARY.md, no book.toml, and no theme path to point anywhere. The sidebar is generated from the directory tree, and ordering is controlled per page with sidebar.order in the front matter.

2. The manifest required

Section titled “2. The manifest ”

manifest.json drives the version selector, the compatibility badges, and the /<repo>/latest/ redirect. Two schema versions are supported side by side; the navbar detects which one it is reading from the presence of manifest_version.

  • v2 — recommended
  • v1 — still supported

Validated against module-manifest-v2.schema.json. Strict — additionalProperties is off everywhere.

kind says what the repository is, and determines how its versions relate to the ABI:

kind Meaning versions entries
contract This repository’s versions are ABI versions no abi, optional note
module / host Targets one or more ABI versions abi required
infrastructure No ABI relation at all no abi, optional note

An abi is either a bare version ("abi": "1.0.0") or an array of anchors ("abi": ["1.0.0", "2.0.0"]) when a version is deliberately built against more than one ABI major.

Other fields worth knowing:

  • metadata.repo is the GitHub repository name, and must match the module’s entry in modules-registry.json.
  • metadata.latest is the version latest resolves to. Update it when you cut a release.
  • A version’s note ("LTS", "security fixes only") is shown under it in the version dropdown.
  • kind takes precedence over the module’s is_abi / meta flags in the registry, which become informational once a module ships a v2 manifest.

Validated against module-manifest.schema.json. No manifest_version or kind; the module’s ABI role comes from modules-registry.json instead.

abi_compatibility lists the ABI versions the entry is compatible with, judged by the same rule as the ABI’s own liara_version_provides(): same major.minor is compatible, an older minor is degraded, a different major is a mismatch.

Only major-level precision — or minor-level, for a 0.x ABI — is meaningful. Declaring "0.2.0" means every 0.2.x release is compatible. Declaring "0.2.1" additionally marks 0.2.0 as degraded rather than compatible.

Note

v1 is fully supported and there is no deadline to migrate. New modules should still use v2 — it is stricter, it carries kind, and it can annotate a version.

In both versions, every key in versions must be dev or an x.y.z string.

3. The prose guide

Section titled “3. The prose guide”

Put one file per page in docs/. index.md or index.mdx becomes the section’s front page; the rest follow. Nested directories become nested sidebar groups.

Every page needs front matter:

Only title is required — the build adds a minimal block if you forget — but description is what search results and social cards show, so write it.

Choosing between .md and .mdx

Plain .md gives you Markdown, asides, code frames and Mermaid — enough for most pages. The components in §4.2 (tabs, steps, cards, file trees) are JSX and need .mdx.

Renaming a page from .md to .mdx does not change its URL.

4. What you can write

Section titled “4. What you can write”

4.1 Asides

Section titled “4.1 Asides”

Four types, in Markdown or MDX. The directive form works in both:

Note

Useful to know, but not urgent.

Do it this way

An aside can carry its own title in brackets.

Danger

Numbered sequences that read as a procedure rather than as a list. Wrap an ordinary ordered list:

API reference

  • Directoryinclude/

      • result.h
  • Directorysrc/
    • …

stableexperimentalremoved — inline, for statuses that would otherwise cost a sentence.

Tabs can be synchronised across a page: give every group the same syncKey and choosing a tab in one switches all of them. The manifest section above uses it.

5. The API reference

Section titled “5. The API reference”

Add a Doxyfile and point INPUT at your headers. The builder overrides the output settings at run time, so the only things that matter are what to read and how to read it:

What the builder overrides

GENERATE_XML, GENERATE_HTML, GENERATE_LATEX, XML_PROGRAMLISTING, OUTPUT_DIRECTORY, INPUT and QUIET are all set by build-docs. There is no HTML_HEADER or HTML_FOOTER to wire up any more — Doxygen no longer generates HTML at all. Its XML is read by the preset and rendered as ordinary Starlight pages.

5.1 Documenting headers

Section titled “5.1 Documenting headers”

Javadoc-style comments. Groups, classes, templates, enums, parameter tables and the standard admonitions (@note, @warning, @deprecated) all render:

5.2 Choosing a layout

Section titled “5.2 Choosing a layout”

The loader supports two layouts. file gives one page per header, and it is what every module is built with today: a C header is a coherent unit, and the page stays short enough to scan. symbol gives one page per symbol, for a C++ surface large enough that a per-header page becomes a wall — at roughly two and a half times the page count.

Not selectable per module yet

The layout is chosen in the preset’s own src/content.config.ts, which is baked into the builder image; a module repository cannot override it, because only astro.config.mjs is copied out of the module. Switching a module to symbol means a change in docs-shared. If you need it, say so — the hook is one line, it just has no consumer yet.

6. Testing before you merge

Section titled “6. Testing before you merge”

There is no local build to babysit, and that is on purpose — reproducing the full toolchain locally is more error-prone than running the real one on a hidden URL.

  1. Open a pull request. When documentation files change, a preview is built and published to /<repo>/pr-<n>/.

  2. The URL is posted as a sticky comment on the pull request, and rebuilt on every push.

  3. If the path filter did not catch your change, add the docs-preview label to force a build.

  4. The preview disappears when the pull request closes.

A preview is the one kind of build that carries its own search index, so you can search the pages you just wrote — see Search.

Checklist for a new module

Section titled “Checklist for a new module”

  1. Add manifest.json with metadata.latest and at least a dev version.

  2. Add docs/index.md — one page is enough to start.

  3. Optionally add Doxyfile and include/ for the API reference.

  4. Add the module to modules-registry.json in docs-shared, so the navbar lists it.

  5. Add the CI caller (CI and deployment).

  6. Open a pull request and read the preview.
