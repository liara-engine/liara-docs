2. Build System

Section titled “2. Build System”

2.1 CMake with Presets

Section titled “2.1 CMake with Presets”

The project uses CMake 3.29 or newer, configured exclusively through presets.

The presets live in the meta repository, as a template from which the bootstrap script generates the workspace’s CMakePresets.json. A module repository does not carry its own: a module is configured as part of the workspace, and a second set of presets per repository would be copies of the same file drifting apart. There is no support for “configure CMake by passing options on the command line”; the generated presets are the supported interface, and the CI invokes them unmodified.

Each non-hidden preset is invokable from the command line and used by the CI. The CI does not pass extra options to CMake; it invokes the preset and the preset is fully sufficient.

2.2 Preset Structure

Section titled “2.2 Preset Structure”

Presets are generated from a single template and organized along three axes: platform and compiler, build type, and linkage:

Suffix BUILD_SHARED_LIBS LIARA_LAUNCHER_MODULE_LOADING
(none) OFF link
-link ON link
-runtime ON runtime

LIARA_LAUNCHER_MODULE_LOADING is an explicit cache variable rather than something inferred from BUILD_SHARED_LIBS, because “built as a shared library” and “loaded at runtime” are two different questions and the middle combination is the one that catches export-macro mistakes.

2.3 Single-Config on Linux, Multi-Config on Windows

Section titled “2.3 Single-Config on Linux, Multi-Config on Windows”

On Linux the Ninja generator is used, and the build type is fixed at configure time: each build type is its own configure preset and its own build tree.

On Windows the Visual Studio generator is multi-configuration, and the build type is chosen at build time. CMAKE_BUILD_TYPE has no effect there, so the Windows configure presets do not set it; the build and test presets carry a configuration field instead, which is the declarative form of --config. One Windows configure preset therefore serves both Debug and Release, and switching between them does not re-resolve dependencies.

The consequence for tooling is that a build preset’s name does not always match its configure preset’s name. Anything that needs the build directory resolves it through the preset file rather than guessing from the name.

2.4 Out-of-Source Builds

Section titled “2.4 Out-of-Source Builds”

Build artifacts go to build/<preset-name>/, not to the source directory. The source tree contains no build output. CMake refuses in-source builds with an explicit error message.

Within a build tree, artifacts are grouped by kind rather than by producing module: executables and shared libraries land in build/<preset>/bin/, static libraries and import libraries in build/<preset>/lib/, with multi-config generators adding a configuration subdirectory to each. The launcher and the modules it may load at runtime are therefore siblings, and the launcher’s rpath is $ORIGIN rather than an absolute path into the build tree — the same arrangement a packaged install needs, established early so that packaging does not have to relocate anything later.

2.5 Compile Commands Database

Section titled “2.5 Compile Commands Database”

CMake generates compile_commands.json for every Linux build. The file is symlinked to the workspace root by the bootstrap script, so that clangd (consumed by VSCode, Neovim, CLion, and other editors) finds it automatically.

This file is also the foundation for clang-tidy, code coverage tools, and SonarCloud’s analysis. It is never committed to the repository but must always be available locally.

3. Dependency Management

Section titled “3. Dependency Management”

3.1 vcpkg in Manifest Mode

Section titled “3.1 vcpkg in Manifest Mode”

External dependencies are managed through vcpkg in manifest mode. Each module repository contains a vcpkg.json declaring its dependencies and a vcpkg-configuration.json pinning the registry baseline.

When CMake configures a project, it invokes vcpkg, which reads the manifest and ensures the declared dependencies are available. The first configuration on a fresh machine downloads and builds the dependencies; subsequent configurations use cached binaries.

Every module repository’s vcpkg-configuration.json pins the same registry baseline, and this is a constraint rather than an observation: the workspace merges the manifests into one and resolves dependencies once, so two modules pinned to different baselines would produce a build in which one of the two silently gets versions it never asked for. The bootstrap script checks that they agree and refuses to proceed if they do not, rather than picking one.

3.2 Why vcpkg

Section titled “3.2 Why vcpkg”

Three options were considered: vcpkg, Conan, and using each distribution’s package manager. The third option is rejected because it produces inconsistent builds across distributions (Ubuntu vs Arch vs Fedora ship different versions of the same library) and because it does not work on Windows without significant friction.

vcpkg is preferred over Conan for this project because:

  • Microsoft maintains it, which means MSVC builds are first-class.
  • Manifest mode integrates cleanly with CMake’s find_package flow.
  • The triplet system (specifying target architecture, build type, static/dynamic linking) is more explicit than Conan’s profiles.
  • The default registry is large enough to cover everything the project needs.

The cost of vcpkg is the initial dependency build, which can be slow on first configuration. This is mitigated by the binary cache.

3.3 Binary Cache

Section titled “3.3 Binary Cache”

vcpkg’s binary caching is enabled in CI through GitHub Actions cache and locally through a per-developer cache directory. Cache keys include the manifest hash, the triplet, and the compiler version, so cache invalidation happens automatically when any of these change.

The cache makes “fresh CI runs” approximately as fast as “incremental builds”, which is essential for the project’s contribute-friendly philosophy: a contributor who waits 20 minutes for CI to validate a typo fix loses interest.

3.4 Submodules and FetchContent: Forbidden by Default

Section titled “3.4 Submodules and FetchContent: Forbidden by Default”

Git submodules and FetchContent are not used for external dependencies. Submodules complicate the developer’s local workflow (easy to forget to update them, conflicts on detached HEADs); FetchContent re-downloads sources on every fresh build, which is the slow path that vcpkg’s binary cache exists to avoid.

The exception: FetchContent is allowed for header-only dependencies that are not in vcpkg’s registry, where the cost of re-downloading a few kilobytes of headers is negligible. This exception is approved on a case-by-case basis through the introduction of a dedicated ADR.

3.5 Dependency List by Module

Section titled “3.5 Dependency List by Module”

Each module’s vcpkg.json declares only that module’s direct dependencies. A dependency belongs to the module that owns the concern, which is what makes the list short: the moment a module needs a library the boundary says belongs elsewhere, the boundary is what is wrong, not the list.

The current target (progressively built up in v0.x):

liara-interfaces: no dependencies. The contract must be includable by anything, including a consumer that has never heard of vcpkg.

liara-core: doctest (test only), tomlplusplus (settings), glm (internal implementation, not exposed across the ABI).

liara-platform: doctest (test only), SDL3.

liara-renderer: doctest (test only), Vulkan-Headers, vulkan-memory-allocator, glslang or shaderc (TBD, only if runtime shader compilation is needed), imgui.

liara-assets: doctest (test only), cgltf or tinygltf (TBD), stb (header-only).

liara-audio: doctest (test only), miniaudio.

The Vulkan SDK itself is not managed by vcpkg; it is a system dependency that the developer installs (instructions in BOOTSTRAP.md).

Logging is deliberately absent from this list: whether liara-core uses spdlog or its own logger is undecided, and the decision is deferred to v0.2 rather than being settled by a line in a manifest.

3.6 Inter-Module Dependencies

Section titled “3.6 Inter-Module Dependencies”

Dependencies between Liara’s own modules are not handled by vcpkg. They are handled differently depending on whether the build is a workspace build (all modules together) or a consumer build (one module installed, another consuming it):

  • Workspace build: the meta repository’s superbuild CMakeLists.txt uses add_subdirectory() to include each module. Inter-module dependencies are resolved as targets in the same build tree.
  • Consumer build: each module installs CMake config files via install(EXPORT ...), and consumers use find_package(LiaraInterfaces REQUIRED) etc.

Both flows are tested in CI, on every push.

4. Reusable Workflows

Section titled “4. Reusable Workflows”

The .github organization-level repository contains reusable GitHub Actions workflows that every module repository invokes. This avoids duplicating CI logic across N repositories.

4.1 Why Reusable Workflows

Section titled “4.1 Why Reusable Workflows”

The alternatives are:

  • Copy-paste the workflow YAML across repositories. Maintenance nightmare; a fix in one repo’s CI does not propagate.
  • Composite actions. Better than copy-paste, but limited in what they can do (no matrix, no jobs).
  • Reusable workflows. Full workflow capabilities, called from consuming repos with parameters. The right tool for this scale.

4.2 Workflow Catalog

Section titled “4.2 Workflow Catalog”

The .github repo contains workflows under .github/workflows/reusable-*.yml. The current catalog, grouped by concern:

Build and quality

Section titled “Build and quality”

  • reusable-build-and-test.yml — assembles the workspace superbuild around the calling repository and runs the matrix of §5.2. Inputs: the calling repository’s name, the matrix (a JSON array of legs, each naming a configure, build and test preset), and the CTest labels to exclude.

  • reusable-lint.yml — clang-format on the calling repository’s tracked sources, and clang-tidy on its translation units against the workspace’s compilation database. Generated files are excluded by pattern, because reformatting a file that is compared byte-for-byte with its generator breaks the check that generated it.

The linkage matrix makes a dedicated shared-library workflow unnecessary: the -link and -runtime legs build every module as a shared library and, for -runtime, make the launcher resolve them through dlopen/LoadLibrary instead of linking them. A separate workflow would duplicate them under another name and drift from them.

Interface integrity (liara-interfaces only)

Section titled “Interface integrity (liara-interfaces only)”
  • reusable-abi-header-portability.yml — every public header compiles standalone, warning-free, as C and C++ across several language standards.
  • reusable-abi-interface-rules.yml — enforces the naming and shape rules from INTERFACES.md.
  • reusable-abi-layout-freeze.yml — freezes struct layouts against a generated golden header, catching accidental ABI-breaking layout changes.
  • reusable-abi-snapshot.yml — snapshots the ABI surface and diffs it against the PR base to compute the required version bump.
  • reusable-abi-report.yml — aggregates the four ABI checks into a single sticky PR comment.

Documentation

Section titled “Documentation”
  • reusable-build-docs.yml / reusable-deploy-docs.yml — build the docs in the builder image and publish them to liara-docs. Composed by reusable-docs.yml.
  • reusable-docs-preview.yml — builds a per-PR documentation preview and posts its URL as a sticky comment.

Release and housekeeping

Section titled “Release and housekeeping”
  • reusable-commitlint.yml — validates conventional-commit format on every PR.
  • reusable-validate-manifest.yml — validates each module’s manifest.json against its schema and checks that the release-please target version exists in it.
  • reusable-generate-docker.yml — builds and pushes a Docker image (used for the documentation builder).
  • reusable-clean-ghcr.yml — prunes untagged container images for a given package, keeping the N most recent versions. Called on a weekly schedule.
  • reusable-docs-preview-cleanup.yml — removes a pull request’s documentation preview directory from liara-docs when the pull request closes.
  • clean-ghcr / preview-tag workflows — prune untagged container images and stale preview tags.

Release automation itself (release-please) is invoked directly from each repository rather than through a reusable workflow; see §9.

Renovate has been added to the organization, and each repository has a renovate.json.

[A SonarCloud analysis workflow is also planned but deferred; see §7.]

4.3 Versioning the Reusable Workflows

Section titled “4.3 Versioning the Reusable Workflows”

Consuming workflows reference the reusable workflows by tag, never by branch. On every release of the .github repository, a follow-up job force-updates major and major.minor tags to point to the new release. A major.minor.patch tag is also created for the release. Major, minor, and patch are defined by release-please’s conventional commit rules: a breaking change bumps the major, a feature bumps the minor, a fix bumps the patch.

A consumer pin the reusable workflow to a specific version by using the @tag syntax in the uses: field. For a large majority of cases, we recommend pinning to @major — which means the consumer will pick up fixes and features, while a change that breaks the interface will require an explicit major version bump in the consumer’s workflow.

Workflows that additionally check out the .github repository to reach a shared script take a github-repo-version input for the same purpose. Callers pass it explicitly, with the same ref they pinned the workflow to; the two must not drift apart, or a workflow will run against a script from a different release.

This protects against the situation where a fix to the CI infrastructure silently breaks every module’s CI on every push.

5. CI Pipelines

Section titled “5. CI Pipelines”

Each module repository has its own CI in .github/workflows/, split into small workflow files (build, lint, docs, commitlint, release) that call the reusable workflows. The per-module files just configure inputs.

5.1 Triggers

Section titled “5.1 Triggers”

The CI runs on:

  • Every push to main.
  • Every pull request targeting main.
  • Every push to a tag matching vX.Y.Z (for release builds).
  • Manual dispatch through the GitHub UI (for debugging).

The CI does not run on pushes to feature branches that are not yet associated with a PR. This avoids burning compute on work-in-progress that the developer is not ready to validate.

5.2 Build Matrix

Section titled “5.2 Build Matrix”

The matrix is expressed as preset names rather than as (OS, compiler, build type) tuples: the presets are the project’s supported build interface, and a CI leg a developer cannot reproduce with one preset name is a leg that lies about what it proves.

Leg Preset What it is there for
linux-gcc-debug linux-debug-gcc Tests, GCC diagnostics
linux-gcc-release linux-release-gcc Optimized build, different warnings
linux-clang-debug linux-debug-clang Tests, Clang diagnostics, cross-language tests
linux-clang-release linux-release-clang Optimized build
linux-shared-link linux-debug-clang-link Export macros: catches a missing LIARA_*_API
linux-shared-runtime linux-debug-clang-runtime Static coupling: the launcher links nothing it loads
windows-debug windows / windows-debug MSVC, multi-config generator
windows-release windows / windows-release MSVC, optimized
windows-runtime windows-runtime / windows-debug-runtime LoadLibrary path and DLL naming

All must pass for the CI to be considered green. The two shared-library legs are not optional extras: they are the only thing standing between “designed for dynamic” and a claim nobody checks.

The matrix uses Ubuntu rather than Arch because GitHub-hosted runners do not offer Arch and self-hosted Arch runners would add operational burden. The promise that “the project supports Arch” is made by the fact that the developer uses Arch daily. A scheduled Arch container job is deferred until the project has a contributor who is not that developer.he matrix uses Ubuntu rather than Arch because GitHub-hosted runners do not offer Arch and self-hosted Arch runners would add operational burden. 5.3 Parallelism and Caching

Section titled “5.3 Parallelism and Caching”

Each matrix job runs independently. Caches are used aggressively:

  • vcpkg binary cache: a per-leg GitHub Actions cache over VCPKG_DEFAULT_BINARY_CACHE, keyed by the runner OS, the preset and the hash of the merged manifest. It invalidates itself when any of those change.
  • Compile cache (ccache / sccache): picked up automatically by the workspace CMakeLists when present, and deliberately not installed in CI. With the current dependency set the build is dominated by the project’s own handful of translation units, and a compile cache would cost more in cache transfer than it saves. Revisit when a build leg exceeds a few minutes.

The total CI time per push, with warm caches, is under 5 minutes per matrix entry, with all entries running in parallel: end-to-end under 10 minutes.

5.4 Required Status Checks

Section titled “5.4 Required Status Checks”

The following checks are required to merge a PR:

  • Every build matrix leg passes, linux-shared-link and linux-shared-runtime included.
  • clang-format produces no diff.
  • clang-tidy produces no new warnings.
  • The test suite passes, cross-language tests included.
  • The ABI checks pass (liara-interfaces only).
  • Coverage: deferred. Measuring coverage of Phase 0’s placeholder implementations would report a number about scaffolding. The gate is introduced in v0.2, alongside the first code worth covering.
  • SonarCloud quality gate: deferred, see §7.3.

Documentation generation is not a required check (a doc-only failure should not block code merges); it runs but only reports.

6. Testing

Section titled “6. Testing”

6.1 doctest

Section titled “6.1 doctest”

The project uses doctest as its test framework. The choice over Catch2 is motivated by compile times: doctest is roughly an order of magnitude faster to compile, and at this project’s scale that difference compounds across every CI run.

Tests are organized as separate executables per module, located in each module’s tests/ directory. Each test executable is a doctest runner, registered with CTest:

Each repository’s test targets are named after what they exercise and the language they exercise it from, because the same contract is tested from more than one:

Modules are consumed through their Liara:: alias, never through the bare target name, so that a test compiles against exactly what a consumer would get.

This integration with CTest means that the same ctest invocation runs all tests across all modules, both locally and in CI.

6.2 Test Categories

Section titled “6.2 Test Categories”

Tests are classified with CTest labels, not with doctest tags. The taxonomy has to cover tests that are not doctest executables at all — the C-only compilation test, the Zig and Rust cross-language tests, the launcher smoke test — so it lives at the CTest level:

A category is then selected with ctest -L unit and excluded with ctest -LE gpu. A test may carry several labels (LABELS "integration;slow").

Categories are:

  • unit: pure unit tests, no I/O, no Vulkan, no OS interaction. Run on every CI build.
  • integration: tests that exercise multiple modules together, may use the file system or load real assets. Run on every CI build but excluded from the developer’s “fast feedback” run.
  • gpu: tests that require a Vulkan device. Run only in CI configurations that have GPU access (currently none on GitHub-hosted runners; this category is reserved for future self-hosted runners).
  • benchmark: performance benchmarks. Run on every CI build with results recorded but not gating.
  • slow: tests that take more than a few hundred milliseconds. Excluded by default to keep the fast feedback loop fast.
  • cross-lang: tests that exercise the C API from a non C/C++ language with a C FFI (python, Zig, Rust…).

Selection is by exclusion, not by inclusion: CI and the developer both run everything and subtract what does not apply (ctest -LE gpu, ctest -LE "slow|gpu"). A test that carries no label therefore runs everywhere, which is the safe default — forgetting a label costs time, never coverage, and the reverse would let a whole repository report success without executing anything.

The corollary is that a label is only worth adding when something is meant to exclude it. unit is carried anyway, because ctest -L unit is the fast loop a developer reaches for while working, and it is the one place inclusion is convenient.

A developer running tests locally typically runs unit only; CI runs everything except gpu (slow may be usually skipped, and used in release PR, for example).

6.3 Test Discipline

Section titled “6.3 Test Discipline”
  • Tests live in the module they test. A test that exercises code from multiple modules lives in the module that initiated the feature being tested.
  • Test files are named test_*.cpp and follow the same code style as production code.
  • Tests are written alongside features, not retrofitted. A PR that adds a feature without tests is not merge-ready.
  • Tests use the public C interfaces of liara-interfaces for integration-style tests, and may use C++ implementation details for module-internal unit tests.

6.4 Coverage

Section titled “6.4 Coverage”

Coverage is collected on Linux GCC Debug builds via gcovr, producing a Cobertura XML report. On Windows, OpenCppCoverage produces an equivalent report.

The coverage reports are uploaded to Codecov, which provides historical tracking and PR comments showing changes in coverage.

The project does not target a specific coverage percentage. The target is direction: each PR should not decrease coverage without justification. This pragmatic approach avoids both the “100% coverage cult” (which produces tests that test the test framework) and the “coverage doesn’t matter” excuse.

The coverage badge on the README links to Codecov. The exact percentage shown is the average across all modules.

7. Static Analysis

Section titled “7. Static Analysis”

7.1 clang-format

Section titled “7.1 clang-format”

Code formatting is enforced by clang-format 20+. The configuration lives in .clang-format at the root of each repository. The configuration is identical across repositories (except for liara-interfaces, which has a C-only configuration for its C headers).

The CI runs clang-format --dry-run --Werror on every C++ source file. Any deviation fails the build. There is no “format on save and commit” optional pre-hook; the CI is the source of truth.

The detailed style is documented in CODE_STYLE.md.

7.2 clang-tidy

Section titled “7.2 clang-tidy”

clang-tidy provides linting beyond formatting: catching common bugs, enforcing modern C++ idioms, flagging anti-patterns. The configuration lives in .clang-tidy at the root of each repository.

clang-tidy runs as part of every CI build, parallelized across source files. The result is filtered to new warnings introduced by the PR: existing warnings in untouched code are reported but not required to be fixed in unrelated PRs. This avoids the situation where every PR has to clean up legacy warnings before being mergeable.

The clang-tidy configuration uses a curated set of checks rather than * (all checks). The selected checks are listed in CODE_STYLE.md with rationale.

7.3 SonarCloud

Section titled “7.3 SonarCloud”

SonarCloud provides a third layer of analysis: bugs, code smells, duplication, security hotspots, and overall maintainability metrics. It complements clang-tidy by tracking trends over time and providing a web UI for exploration.

SonarCloud is free for open-source projects. Each module repository is a separate SonarCloud project, and the meta repository displays aggregate badges in its README.

The SonarCloud quality gate is configured to fail the CI if:

  • New code coverage falls below 80%.
  • New code introduces critical bugs.
  • New code introduces security vulnerabilities.
  • New code’s reliability rating is below A.

Existing-code metrics are not gated; only new code (the diff in the PR) is judged. This makes SonarCloud’s feedback actionable without becoming a blocker on every PR.

8. Conventional Commits

Section titled “8. Conventional Commits”

The project uses Conventional Commits 1.0. Commit messages follow the pattern:

The header is mandatory; the body and footer are optional. Lines are wrapped at 72 characters.

8.1 Types

Section titled “8.1 Types”

The accepted types are:

  • feat: a new feature visible to consumers.
  • fix: a bug fix.
  • docs: documentation changes only.
  • style: code style changes (formatting, missing semicolons; not used much because clang-format makes most of these unnecessary).
  • refactor: code changes that are neither features nor fixes.
  • perf: performance improvement.
  • test: adding or modifying tests.
  • build: changes to build system, vcpkg, CMake.
  • ci: changes to CI configuration.
  • chore: routine maintenance.
  • revert: reverts a previous commit.

8.2 Scopes

Section titled “8.2 Scopes”

Scopes identify the area of the project a commit affects. In a multi-repo layout, scopes correspond to subsystems within a module.

Some examples of possible scopes (not exhaustive):

In liara-core:

  • ecs, math, logger, settings, events, loop.

In liara-platform:

  • window, input, timing, signals.

In liara-renderer:

  • device, swapchain, pipeline, passes, targets, imgui, debug.

In liara-assets:

  • loading, decoding, lifetime, mesh, texture.

In liara-audio:

  • playback, mixing, sources.

In liara-interfaces:

  • core, platform, renderer, assets, audio, physics, version, types.

In liara (meta):

  • launcher, docs, packaging, scripts.

Cross-cutting scopes available everywhere: build, ci, deps.

A scope names a concern inside one repository. It never names another module: a commit in liara-core scoped assets would be describing work that belongs in liara-assets, and the scope is the first place that mistake becomes visible.

8.3 Breaking Changes

Section titled “8.3 Breaking Changes”

A breaking change is signaled in two ways: the type is suffixed with ! (e.g., feat(renderer)!: change packet structure) and the footer contains a BREAKING CHANGE: block describing the impact. Both signals are required.

For modules that expose interfaces (most of them), a breaking change in the conventional-commits sense triggers a major version bump through release-please.

8.4 Validation

Section titled “8.4 Validation”

Conventional commit format is validated by commitlint, run in CI as part of the lint workflow. Non-conforming commits fail the PR’s checks. There is no Husky pre-commit hook because Husky requires Node.js in every developer’s environment, which adds friction.

In the same workflow, a manifest validation step checks that the manifest.json file is valid JSON and conforms to the schema in manifest.schema.json. It also checks that the version in the manifest matches the version release-please is about to tag. This ensures that the manifest is always correct and up-to-date before a release.

9. Release Automation

Section titled “9. Release Automation”

9.1 release-please

Section titled “9.1 release-please”

Each repository is configured with release-please, Google’s release automation tool. The configuration lives in release-please-config.json at the repo root, with a manifest at .release-please-manifest.json tracking the current version.

release-please works by maintaining a “release PR” that accumulates changes from conventional commits. When the release PR is merged, a new version is tagged, a changelog entry is created, and a GitHub release is produced.

Each repository has its own independent release cycle. There is no synchronization between modules’ versions.

9.2 Multiple Packages in One Repository

Section titled “9.2 Multiple Packages in One Repository”

The meta repository is the only one that releases more than one thing. Its release-please-config.json declares four packages — the repository itself (.), docker/, schemas/ and launcher/ — with separate-pull-requests enabled, so each accumulates its own release PR and its own line in .release-please-manifest.json. The root package lists the other three in exclude-paths, so a change to the documentation builder does not bump the engine’s version.

Only the root package produces plain vX.Y.Z tags. The other three carry their component in the tag (docker-v1.2.3, schemas-v0.1.1, launcher-v0.0.1); the Docker image workflow triggers on docker-v*.

Two CMake consequences follow. Each CMakeLists.txt reads its version out of .release-please-manifest.json rather than hard-coding it, and the launcher reads the launcher key of the meta repository’s manifest rather than the root one.

9.3 Changelog Generation

Section titled “9.3 Changelog Generation”

release-please generates CHANGELOG.md automatically from conventional commits. The format follows Keep a Changelog. Each release section lists features, fixes, and breaking changes, grouped by scope.

The generated changelog is reviewed in the release PR before merging. Manual edits are possible but rare; the discipline of writing good commit messages produces good changelog entries automatically.

9.4 Release Artifacts

Section titled “9.4 Release Artifacts”

When release-please merges a release PR and creates a GitHub Release for a module, a follow-up workflow builds that module’s binaries and attaches them to the release. This turns every module release into a set of consumable, precompiled artifacts rather than a source-only tag.

What is published, per module release:

Section titled “What is published, per module release:”
  • The compiled library, for each supported platform and toolchain: Linux/GCC, Linux/Clang, Windows/MSVC.
  • Both the static and the shared build of the library, so that a consumer can choose to link statically or to compose a runtime from shared modules.
  • The module’s public headers.
  • The module’s manifest.json for the released version, which records its ABI compatibility. This is the machine-readable record a composition step reads to validate a combination (see below and ROADMAP.md).
  • A checksum file (SHA-256) covering every artifact in the release.

What triggers it:

Section titled “What triggers it:”

The workflow runs on the release published event, keyed to the tag release-please created. It does not run on every push: only tagged releases produce artifacts, which keeps storage bounded and makes “a released version” and “a set of downloadable binaries” the same thing.

Naming:

Section titled “Naming:”

Artifacts follow a stable, parseable convention: liara-<module>-<version>-<platform>-<toolchain>-<linkage>.<ext> (for example liara-core-0.3.1-linux-clang-shared.tar.zst, liara-renderer-0.3.0-windows-msvc-static.zip). The convention is stable because the composition tooling parses it; a change to it is a breaking change to that tooling.

What is deliberately not here:

Section titled “What is deliberately not here:”

These are per-module artifacts, not a bundled engine. Assembling a specific set of module versions into a runnable engine — for compatibility testing, or for a user with a specific need — is the job of the composition script, which consumes these artifacts rather than producing them. It is described in ROADMAP.md, not here, because it is a developer/user tool rather than CI infrastructure.

10. Documentation Generation

Section titled “10. Documentation Generation”

See DOCUMENTATION_PIPELINE.md for the full documentation generation and deployment pipeline.

11. Branch Protection and Required Reviews

Section titled “11. Branch Protection and Required Reviews”

11.1 Main Branch

Section titled “11.1 Main Branch”

Each module repository’s main branch is protected:

  • Direct pushes are forbidden.
  • All changes go through pull requests.
  • All required CI checks must pass before merge.
  • Force pushes are forbidden.
  • Branch deletion is forbidden.

The “required reviews” rule is set to zero for solo development: the developer reviews their own PRs, the CI is the gatekeeper. If the project gains contributors, this is revisited and at least one review is required.

11.2 Squash Merge Only

Section titled “11.2 Squash Merge Only”

Pull requests are merged via squash-and-merge. This produces clean linear history on main, with each PR appearing as one commit. The commit message of the squash uses the PR’s title (which itself follows conventional commits) and the PR description as the body.

This avoids the noise of “fix typo”, “respond to review comment” commits cluttering the history, while preserving the information in the PR’s discussion.

11.3 Tag Protection

Section titled “11.3 Tag Protection”

Tags matching v*.*.* are protected. Only release-please can create them, through its merge-the-release-PR mechanism.

Two other tag namespaces exist and are deliberately outside that protection: preview-<pr-number>, force-updated on every push to a pull request so that a workflow under review can be called by its preview tag, and the floating vX / vX.Y tags described in section 4.

12. Local Development Workflow

Section titled “12. Local Development Workflow”

12.1 The Local CLI

Section titled “12.1 The Local CLI”

Every local operation goes through a single entry point: ./scripts/liara.sh on Linux, .\scripts\liara.ps1 on Windows. Both are thin wrappers around scripts/liara.py, which is where the logic lives — there is no platform-specific duplicate to keep in sync. The subcommands are verify, setup, build, test, launch, clean and check.

12.2 Workspace Setup

Section titled “12.2 Workspace Setup”
  1. Clone the meta repository.
  2. Run ./scripts/liara.sh verify to confirm the environment (--optional also checks the recommended-but-not-required tools).
  3. Run ./scripts/liara.sh setup. This clones every module repository into workspace/, generates the superbuild CMakeLists.txt, a merged vcpkg.json (the union of every module’s dependencies and features), and the workspace-level CMakePresets.json, then configures CMake and — on Linux — symlinks compile_commands.json at the workspace root. vcpkg dependency resolution happens during that configure step. --preset overrides the preset, --no-configure stops before CMake, --no-pull leaves existing clones untouched (useful while working on a branch), and --ssh clones over SSH. Re-running the script is safe and is the standard way to refresh the workspace.
  4. Open workspace/ in the editor of choice.

The Visual Studio generator does not produce a compile_commands.json, so the symlink step is skipped on Windows and clangd-based tooling there needs a Ninja configuration of its own.

12.3 Pre-Commit Checks

Section titled “12.3 Pre-Commit Checks”

The project does not require pre-commit hooks. The CI is the source of truth, and ./scripts/liara.sh check runs the same checks locally, in this order: clang-format, build, clang-tidy, CTest. The build comes before clang-tidy because clang-tidy consumes the compile_commands.json that the build produces. --fix applies formatting instead of only reporting it; --no-format, --no-build, --no-tidy and --no-tests skip a step; --preset overrides the preset. The exit code is 0 only if every enabled step succeeded.

12.4 Compile Cache

Section titled “12.4 Compile Cache”

The generated workspace CMakeLists.txt selects a compiler cache — sccache if present, otherwise ccache — and a linker — mold, otherwise lld — before creating any target, which is the only point at which those settings take effect. Nothing is configured by the presets themselves. Both are picked up from PATH and both are optional: their absence is silent.

12.5 Editor Integration

Section titled “12.5 Editor Integration”

The project supports any editor that consumes compile_commands.json:

  • CLion: opens the workspace CMakeLists.txt directly.
  • VSCode: with the C/C++ extension or clangd extension.
  • Neovim: with clangd via nvim-lspconfig.
  • Vim: with vim-lsp or coc.nvim configured for clangd.

The .clang-format and .clang-tidy files at each repo root drive the editor’s formatting and linting. No editor-specific configuration is committed to the project.

13. Performance Tracking

Section titled “13. Performance Tracking”

13.1 Benchmark Results in CI

Section titled “13.1 Benchmark Results in CI”

The benchmark suite ([benchmark] test category) runs in CI on every push to main. Results are logged as artifacts and, longer term, plotted on a dashboard so that performance regressions are visible.

The dashboard is not yet built in v0.x. The initial plan is to log results as JSON files attached to CI runs and to write a small script that fetches and plots them on demand. A proper dashboard (perhaps deployed alongside the docs hub) is deferred to v1.x.

13.2 Continuous Profiling

Section titled “13.2 Continuous Profiling”

No continuous profiling is set up in v0.x. Profile data is captured manually when a developer notices a performance issue. The [benchmark] tests serve as a coarse early warning: a 2x regression in a benchmark is visible in the CI logs.

14 What Is Explicitly Not Used

Section titled “14 What Is Explicitly Not Used”

To avoid the temptation of adding tools “just because they exist”:

  • No conan: vcpkg fills the role.
  • No bazel, meson, premake, or other build systems: CMake is sufficient.
  • No Husky or pre-commit hooks framework: CI checks are the source of truth.
  • No Jenkins, GitLab CI, CircleCI: GitHub Actions is sufficient and is where the code lives.
  • No proprietary code analysis tools beyond SonarCloud’s free tier.
  • No package signing infrastructure (deferred until there is a real need).
  • No Docker for the runtime (the engine is not containerized; Docker is used only for CI image consistency, not for shipping).

Each “not used” entry is the result of an explicit decision. If a new contributor proposes adding one of these, they should reference the relevant section of this document and explain what changed.
